# 01 策略与设计

> 实验目录：`2026-10-30_23-00-Omni7B-SFT-GRPO`
> 对照基准：`2026-10-29_14-21-GRPO`（3B，第一轮 GRPO，最优检查点 `step_0050`）
> 本文只讲**怎么设计、为什么这么设计**。实际跑了什么见 `02_训练记录.md`，跑出来什么见 `03_结果分析.md`。

---

## 一、要回答的问题

课程基线 SFT 是 **Qwen2.5-Omni-3B + LoRA**。此前三轮（GRPO R1、GRPO R2、PPO）都建立在它之上，几轮分析得出一个猜测：主要瓶颈不在强化学习算法，而在**模型看视频这一路的准确率** —— 验证集 666 条里有 55 条视觉情绪读反（8.3%），而且约 65% 的冲突判定错误由它传导下去。

于是问题变成：

> **换一个更大的模型，能不能把这一层直接抬起来？**

为此设计一个**只改模型、不改配方**的对照：

```
课程基线的 SFT 配方  ×  Qwen2.5-Omni-7B   →  SFT  →  CSV #1
                                          ↓
                     第一轮 GRPO 的 step50 配方  →  第 50 步  →  CSV #2（对齐 3B 口径）
                                                └  第 150 步  →  CSV #3（验证集峰值）
```

## 二、对照设计：什么被严格固定，什么允许变

这是整件事最重要的部分。为了让"3B → 7B"成为唯一变量，下列内容**逐字未改**：

| 维度 | 内容 | 状态 |
|---|---|---|
| SFT 数据 | 3352 训练 / 666 验证，同一个 `training_dataset/Dataset` | 未改 |
| SFT 混合 | 8730 条/轮 = 完整 3352 + 纯画面 2103 + 纯文本 1702 + 纯音频 1573，权重 2/3、1/9、1/9、1/9 | 未改 |
| 训练轮数 | 3 epoch，546 步/轮，共 1638 步 | 未改 |
| 有效 batch | 16（micro 4 × 累积 4） | 未改 |
| LoRA | r=16，α=32，dropout=0.05，挂在语言 attention/MLP + visual.blocks + audio_tower.layers | 未改 |
| 优化器 | AdamW，lr=1e-4，cosine，warmup 3%（50 步），wd=0.01，clip=1.0，seed=42 | 未改 |
| 输入 | 8 帧、最长边 448、16kHz 单声道、最长 4096 token、禁止截断 | 未改 |
| 评测 | greedy，最多 192 token，666 条全量 | 未改 |
| GRPO 奖励 | `reward.py` 逐字未改（0.35/0.10/0.10/0.45，一致性 −0.05，非法 JSON −0.20） | 未改 |
| GRPO 采样 | 2 prompt/步 × 8 候选，temp 1.1，top_p 0.95，max_new 128 | 未改 |
| GRPO 优化 | lr 2e-6，2 PPO epoch，clip 0.2，KL β 0.02，优势 ×1.5 | 未改 |
| GRPO 调度 | 300 步，每 50 步评测，F1 护栏 0.01，seed 42 | 未改 |

**只允许三件事变化，其中两件是工程适配，一件就是实验本身：**

1. **基座模型**：3B → 7B。这是实验目的。
2. **评测的生成 batch**：16 → 8。不进梯度，理由见第四节。
3. **GRPO 的显存适配**：策略模型开梯度检查点；logprob 改分块 log_softmax。

第 3 条必须解释清楚，否则会被当成改了算法：

- **梯度检查点**只改"存不存中间激活"，不改前向/反向的数学。但它只在 train 模式下生效，而 GRPO 又需要 dropout 关闭来保证 old/ref logprob 可复算 —— 所以用 `grad_pass()` 把 LoRA dropout 临时置 0 再切 train，退出时复原。
- **分块 log_softmax**：原实现把 `[seq, vocab]` 整块 `float()` 后做一次 `log_softmax`，7B 上这块额外要 4~5 GB。改法是对序列位置按 512 分块，每块单独 `float()` 再 `log_softmax`。bf16→fp32 是无损转换，**逐块与整块的结果逐位相同**，不是近似。

## 三、起点关系：与 3B 三轮并列，不串联

```
Combined-SFT-3B ──┬── GRPO R1 (2026-10-29_14-21)   ← 本次的 GRPO 配方来源
                  ├── GRPO R2 (2026-10-29_23-22)
                  └── PPO     (2026-10-30_13-39)

Combined-SFT-7B ── SFT 复刻（本轮）──┬── CSV #1（纯 SFT）
                                     └── GRPO step50 复刻 ──┬── CSV #2（第 50 步）
                                                             └── CSV #3（第 150 步，验证集峰值）
```

7B 的 GRPO **只接在 7B 自己的 SFT 上**，不碰 3B 的任何产物。这样"算法增益"才可比：同一套 SFT 配方、同一套 GRPO 配方，差别只有模型。

## 四、为什么只动评测 batch，不动训练配方

7B 的 Thinker 权重（bf16）约 17.2 GB，是 3B 的两倍多；梯度检查点因此是必需项，不是可选项。但**训练侧的超参一个都没动**：micro-batch 4、累积 4、有效 batch 16，与 3B 第一轮逐项相同。

唯一的改动在评测侧：batch 16 → 8。这不是「跑不动就调小」的权宜之计，准确的说法是：

**它不进梯度，因此不属于配方的一部分。** 决定学到的权重的是训练侧 micro-batch 与累积步数，这两项保持原值。而在评测里，greedy 解码逐行独立、padding 被 `attention_mask` 屏蔽、推理没有 batch 相关的归一化，所以改变一次前向喂几条，不可能改变任何一条样本的输出分布。

严格讲唯一可能的差异是不同 batch 形状下浮点归约顺序不同，导致近似并列的结果翻转。这个量级远低于本实验的分辨率，但不等于数学上的零。

**这条后来被实测了**：同一份权重（`checkpoint-1638`）在两条评测链路上各评一遍 —— SFT 链路 batch 8，GRPO 基线链路 batch 4 —— 666 条里**只有 1 条预测不同**（`ch_sims_v2:VA:aqgy5_0024:00012`，视觉正/负近似并列被翻转），输出 token 长度完全相同，综合分 0.9055 vs 0.9052。

所以准确表述是：**不与结果挂钩，但差值不是零，量级约 0.15%（1/666）**。凡是跨模型比较，两侧都取同一条链路（GRPO 基线，batch 4），这条 1/666 的噪声因此被抵消。

## 五、预检：正式训练前的强制门

课程基线脚本自带 pilot 阶段，`summary.json` 里 `passed: true` 才继续。这次全部通过：

| 检查 | 结果 |
|---|---|
| 可训练参数 | language 40,370,176 / vision 12,462,080 / audio 11,796,480 |
| 视觉、音频两组是否与 3B 一致 | **一致**（3B 也是 12,462,080 / 11,796,480）→ 印证两个尺寸共用同一套编码器 |
| 选位置 CE 是否等于全量掩码 CE | 相等 |
| 尾部累积梯度是否等于整批梯度 | 相等 |
| 六种 batch 组合（VT+V+T+A / VA+V+T+A / full_VT / full_VA / vision_only / text_only / audio_only）梯度是否非零 | 全部非零，且缺失模态的组严格为零 |
| 保存 adapter 再重载，logits 是否一致 | 完全相等 |
| 数据 | 训练 3352 / 验证 666；混合 8730 = 3352 + 2103 + 1702 + 1573，与 3B 那轮逐项相同 |

`vision` 与 `audio` 两组可训练参数与 3B 分毫不差，是本轮最重要的一个事实：**3B 与 7B 共用同一套视觉塔与音频编码器，只有语言塔不同。** 这条决定了结果应该怎么解读（见 `03_结果分析.md` §10）。

## 六、代码改动清单

`code/sft/` 是课程基线仓库 `model_repo/code/` 的完整拷贝（14 个文件），只改 4 处：

| 文件 | 改动 | 原因 |
|---|---|---|
| `train_omni_combined_sft.py` | `attach()` 的可训练参数断言 | 原来写死 3B 的 `{language: 29933568, vision: 12462080, audio: 11796480}`。7B 语言塔不同，但视觉塔与音频编码器同规格，所以保留这两个数做严格校验，语言数只记录不写死 |
| 同上 | `model_id`、`micro_batch` 改为参数 | 3B 的常量直接搬会写错模型名，也会失去显存回退能力 |
| 同上 | wandb 改为可关闭（默认 disabled） | 离线环境下 `mode='online'` 会卡住；换成空实现，其余日志照常落盘 |
| 同上 | pilot 的 batch 循环支持 micro-batch 切片 | 预检必须与正式训练同 micro-batch，否则预检结论失效 |

`code/grpo/train_grpo.py` 是 3B 第一轮 GRPO 的拷贝，改动集中在设备与显存：

| 改动 | 说明 |
|---|---|
| `--code` | 指向 `code/sft`，保证预处理、系统提示、严格 JSON 解析与训练一致 |
| `--policy-device / --reference-device` | 两个模型分居不同设备（3B 时写死 cuda:0） |
| `--media-cache` | 允许解码缓存放到输出目录之外，避免重跑时被搬走（PPO 轮踩过） |
| `load()` | 策略模型开非重入梯度检查点 |
| `logprobs()` | 分块 log_softmax（等价改写） |
| `grad_pass()` | 训练期临时关 LoRA dropout，保证 old/ref 与训练前向一致 |
| 可训练参数断言 | 从"必须等于 54,192,128"改为"必须全部是 LoRA 且数量 > 0"，实际值写盘 |

`code/make_submission.py` 直接复用 3B 那轮的提交脚本（提示词、字段解析、问句模板都来自 `code/sft`），只把 `--base` 换成 7B。

新增 `code/analyze_results.py`：只依赖本地产物，用官方 `score()` 重算本文档与 `03` 里的每一个数字。

## 七、运行保障

- **两个路径视图**（内容完全不变，只解决目录布局）：
  - 训练脚本要求 `--data` 目录同时含 `train_pool.jsonl`（混合清单）与两个 manifest，而上游分放在 `data/` 与 `manifests/`。用 `sft_run/data_view/` 放三个软链接合到一起。
  - 脚本的 `validate()` 断言每条视频 `resolve()` 后仍在 `--dataset` 之内，而上游 `Dataset/videos` 是指向外部目录的软链接，断言必然失败。用 `sft_run/dataset_view/`：jsonl 软链（仍是同一份 3352/666 行），`videos/` 用 `cp -al` 做硬链接树（同 inode，不占额外空间）。**改的是路径，不是数据。**
- **媒体缓存复用**：`prepare_media` 是内容寻址（`sha256-f8-s448`），直接复用课程基线 SFT 的缓存，不必重新解码。
- **串联队列**：SFT 之后的所有步骤排成一支队列（`scripts/chain_after_sft.sh`）自动接力。顺序是刻意安排的：**先出 CSV #1 再开 GRPO** —— 两者同时启动会在权重加载的窗口里互相拖慢。
- **队列的两道保护**：SFT 进程消失但状态不是 complete 时立刻失败退出（不会静默等到天亮）；`step_0050` 不存在时回退到 `best.json` 并记一条 WARN。
