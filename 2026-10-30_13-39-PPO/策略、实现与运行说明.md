# PPO 训练策略、实现与运行说明

本文件记录 `2026-10-30_13-39-PPO` 这一轮实验的**全部设计决策**：为什么用 PPO、怎么把 PPO 落到
Qwen2.5-Omni-3B 上、每个超参为什么取这个值、工程上怎么保证正确性与可复现性。
结果与审计数据见 `GRPO_PPO对比与训练记录.docx` 与 `runs/pilot_01/AUDIT.md`。

## 0. 一句话总结

在课程基线 Combined-SFT 适配器（Kaggle 0.93049）之上，用**真正的 PPO**（学习式批评家 + GAE + 逐 token
裁剪）继续训练 54,192,128 个 LoRA 参数，目标是在不破坏情绪分类的前提下提升**模态冲突判定**能力。

## 1. 为什么在 SFT 上做 PPO

### 1.1 起点

| 项目 | 内容 |
|---|---|
| 基座 | Qwen2.5-Omni-3B（Thinker 部分，不含 Talker） |
| 起点策略 | 课程基线 Combined-SFT 适配器，LoRA r=16 / α=32，54,192,128 参数 |
| 训练集 | 3352 条（原始 2980 + 合成增强 372），验证集 666 条 |
| 奖励 | 课程基线自带的四字段复合奖励（融合 0.35 / 视觉 0.10 / 第二模态 0.10 / 冲突判定 0.45） |

PPO 只动 LoRA，基座与参考模型全程冻结。

### 1.2 前两轮 GRPO 暴露的问题

第一轮（300 步）与第二轮（600 步，配额改造后）都拿到了正向但不显著的增益：

- 第二轮最好的检查点把冲突召回从 57/74 提到 60/74，原始冲突（真难的那部分）从 10/25 到 13/25；
- 但配对 bootstrap 的 95% 区间下界仍为负（[−0.0016, +0.0295]），且特异度在整轮里单调下滑
  （0.9071 → 0.8986），说明模型在往"多报冲突"漂。

根因不在算法公式，而在**梯度信号的来源**：GRPO 用"同一 prompt 的 4 个候选"的组内均值做基线，
一旦 4 个候选得分相同，advantage 恒为 0，这一整次采样就被丢弃。第二轮 600 次尝试里
**81% 的组方差为零**，2496 个候选只有 193 组真正产生了梯度。

### 1.3 为什么换 PPO

PPO 把基线从"组内蒙特卡洛均值"换成**学习出来的状态值函数 V(s)**，由此得到三点结构性改变：

1. 不再需要组内方差。哪怕 4 条样本得分完全一样，只要 V(s) 与回报有偏差，就有梯度。
2. 信用分配细到 token。GRPO 把整条回答给一个标量优势；PPO 用 GAE 把终局奖励沿回答反向摊开。
3. 样本不再被丢弃。每个 rollout 都同时是策略样本和价值回归目标。

## 2. 算法设计

### 2.1 与 GRPO 的四处结构性差异

| 维度 | 前两轮 GRPO | 本轮 PPO |
|---|---|---|
| 基线 | 同一 prompt 的 4 候选均值（组内） | 学习式批评家 V(s_t)（逐 token） |
| 优势 | 组内标准化标量，整条回答共用一个值 | GAE(γ=1, λ=0.95) 逐 token |
| 批次构成 | 1 个 prompt × 4 候选 | 4 个不同 prompt × 各 1 条 |
| 零方差处理 | 整组丢弃（第二轮丢弃 81%） | 不丢弃，全部进入价值回归 |

### 2.2 奖励分配：终局标量 → token 级

奖励函数本身不改（严格沿用课程基线的复合奖励）。但 PPO 需要逐 token 的奖励信号，因此采用 RLHF 的标准约定：

```
r_t = 0        (t = 0 ... T-2)
r_T = R        (整条回答的四字段复合奖励，取值 [-0.2, 1.0])
```

如果把 R 复制到每个 token，等效奖励会被序列长度（约 26 token）放大 26 倍，梯度尺度直接失控。
只在末尾给一次、再用 GAE 反向传播，是等价的信用分配，但数值上安全得多。

### 2.3 GAE

对单条回答（一个 episode，末端终止，V(s_{T+1}) = 0）：

```
δ_t     = r_t + γ·V(s_{t+1}) − V(s_t)
A_t     = δ_t + γ·λ·A_{t+1}
R̂_t     = A_t + V(s_t)        ← 价值头的回归目标
```

γ=1.0：回答内部不存在折扣需求（一整个回答就是一个决策）。
λ=0.95：偏差-方差折中，26 token 的回答里第一个 token 的 advantage 约为终局奖励的 0.95²⁵ ≈ 27.7%。

**这个数在烟测里被直接验证过**：贪心解码得到 reward=1.0 的回答，critic 初始全零，
测得 `adv_first = 0.27739`，与 0.95²⁵ = 0.2774 完全吻合，说明 v-token 对齐没有错位。

### 2.4 损失函数

一次 update 同时优化三件事（每项在 batch 内取平均）：

```
ratio      = exp(clip(log π_new − log π_old, ±20))
L_policy   = −mean( min(ratio·A, clip(ratio, 1−ε, 1+ε)·A) )        ε = 0.2
L_value    = 0.5·mean( max( (V−R̂)², (V_clip−R̂)² ) )               V_clip = V_old ± 0.2
L_kl       = mean( exp(log π_ref − log π_new) − (log π_ref − log π_new) − 1 )    ← k3 估计量
L          = L_policy + β·L_kl + c·L_value                          β = 0.02, c = 0.5
```

- KL 用 **k3 无偏估计量**（`exp(−δ)+δ−1`，δ = logπ_new − logπ_ref），恒非负，比 k1 更稳。
- 价值损失用**双裁剪**：只信 V 在 V_old 附近 ±0.2 的变化，防止 critic 在单批次上剧烈跳变。
- 优势**不做 batch 级标准化**。这是有意为之：标准化会让"奖励更高的回答获得更大权重"这一性质消失，
  退化成组内相对比较，正是 GRPO 被诟病的地方。奖励尺度本身只有 [-0.2, 1.0]，配合 2e-6 的学习率不需要再缩放。

### 2.5 批评家设计

```
ValueHead = LayerNorm(2048) → Linear(2048 → 1)      zero-init，共 6,145 参数
V(s_t)    = ValueHead( hidden_states[-1][t] .detach() )
```

三个关键决定：

1. **共享 backbone**。独立加载一个 3B 价值模型会让两份模型彻底放不下，
   共享 backbone 只多 6,145 个参数和约 1 MiB 激活。
2. **输入 detach**。价值损失的梯度只流向 value head，绝不回传进 LoRA。
   这样策略梯度和价值梯度严格分离，不会互相污染——这是共享 backbone 方案能否成立的前提。
3. **零初始化**。初始 V≡0，等价于"以 0 为基线的 REINFORCE"起步，再由价值回归逐步学出真实基线；
   避免随机初始化带来的初始优势偏移。

value head 的输入取 `hidden_states[-1]` 在 `prefix−1 : prefix−1+L` 的切片，与策略 logits 的切片**完全同一段**。
因果语言模型里位置 t−1 的隐状态预测第 t 个 token，价值和策略必须共享这个对齐，错一位就会让 critic 学到
"上一个 token 的回报"，advantage 全错。

## 3. 决策记录（为什么是这些数）

### 3.1 为什么 batch 是"4 个不同 prompt"而不是"1 prompt × 4 候选"

后者是 GRPO 的形状。如果 PPO 也这么做，等于只用一个 prompt 的样本来估计梯度，方差极大；
而且 4 条同 prompt 回答高度相关，价值头在同一状态上要拟合 4 个不同回报，会互相拉扯。
改成 4 个不同 prompt 后，一个 update 覆盖 4 个不同难度、不同模态组合的场景，梯度更有代表性。
代价是与 GRPO 的"每步生成条数"相同（都是 4 条），因此两轮训练时间可比。

### 3.2 为什么两个优化器

LoRA 的学习率是 2e-6（相对 3B 模型的常规量级），而 6,145 参数的 value head 用 2e-6 会几乎不动
（实测梯度范数在 3–5，但参数只有几千个，学习需要更多步）。所以：

- `AdamW(lora_params, lr=2e-6)` — 策略
- `AdamW(value_head.parameters(), lr=1e-3)` — 批评家

一次 `loss.backward()` 之后两个优化器各自 step。梯度裁剪也分开做（各自 1.0）。

### 3.3 为什么采样配额从 75/5/20 改成 65/5/30

GRPO 第二轮用 75% 原始冲突，是因为组内方差只在冲突样本上才出现（一致样本上 4 个候选几乎全对）。
PPO 不需要靠冲突样本"制造方差"——一致样本上 V(s) 与回报的偏差本身就是梯度。

而两轮 GRPO 的共同病症是特异度下滑（0.9071 → 0.8986），也就是对**一致样本**误报冲突。
一致样本是唯一能把 `is_conflict` 往回压的数据。所以把一致样本从 20% 提到 30%，冲突总量降到 65%：

| 桶 | GRPO R2 | PPO | 理由 |
|---|---|---|---|
| 原始冲突（143 条，未增强） | 75% | 65% | 仍是最主要的提升目标，但不再需要压倒性占比 |
| 合成冲突（268 条） | 5% | 5% | 模型在合成冲突上已接近饱和（47/49），多给是浪费 |
| 一致样本（2941 条） | 20% | 30% | 抑制误报上升 |

配额按 100 个 prompt 一个计划单元精确执行，原始冲突队列循环取样，600 个 prompt 可覆盖全部 143 条。

### 3.4 为什么 ppo_epochs = 2

PPO 的精髓是用同一批数据多跑几个 epoch，但 3B 模型在温度 1.2 的采样上，token 级 ratio 在 3–4 个 epoch
后就会大量撞上裁剪边界（clip fraction 升高、有效梯度下降）。本轮取 2：比 GRPO 常见的 1 更能体现
PPO 的样本复用优势，又不至于滑出信赖域。实测全程 clip fraction 保持在很低水平（见审计第 4 节）。

### 3.5 为什么 temperature = 1.2，max_new_tokens = 128

- 温度：1.2 比 SFT 推理时的贪心更分散，能给 critic 提供有区分度的回报分布；再高（1.45）会显著增加
  非法 JSON 的比例。
- 长度上限：四字段 JSON 实测 26–40 token，128 留足冗余，同时把最坏情况的显存和时间封顶。

### 3.6 为什么不做 advantage 归一化 / 不做奖励塑形

见 2.4 末段。额外理由：本轮的核心问题是"判定冲突过于保守（漏检 17 条）与过度误报（49 条）并存"，
奖励函数已经把决策权重压到 0.45，再手工放大决策信号会重复 GRPO 第二轮"decision_scale ×1.5"的做法
——那一轮实际只影响了 13.5% 的组。这里让奖励原样进入 PPO，把"该往哪走"交给 critic 和 clip 决定。

## 5. 工程实现

### 5.1 一次前向同时产出策略与价值

```
forward_terms(model, prompt, answer, grad, need_values):
    logits = model(prompt+answer, output_hidden_states=need_values).logits[prefix-1 : prefix-1+L]
    logprob = log_softmax(logits).gather(answer_ids)
    values  = ValueHead(hidden_states[-1][prefix-1 : prefix-1+L])
```

reference 模型不需要 value，传 `need_values=False`，避免白算 hidden states。

### 5.2 两份模型不能同设备共存

价值头只多 6,145 个参数，代价可以忽略；但 policy 与 reference 必须分设备承载，这一点沿用上一轮结论。

### 5.3 校验链

| 阶段 | 内容 | 结果 |
|---|---|---|
| 编译 | `py_compile` 四个文件 | PASS |
| 单元测试 | 11 项（GAE 解析解、终局奖励、配额、批内去重、严格 JSON、配对评测） | 11/11 PASS |
| 数据 | `--check-data`：3352/666、冲突 411、路径存在 | PASS |
| 资产 | `--check-asset`：3 分片、1336 张量、54,192,128 参数、F32 | PASS |
| 环境 | `--check-env`：torch 2.8.0 / transformers 4.57.6 / peft 0.17.1，bf16 | ready=true |
| 真实烟测 | VT/VA 生成 + 真实 PPO 更新 | PASS（见下） |

烟测的关键产出：

- VT/VA 贪心解码均得到合法四字段 JSON（reward = 1.0）；
- critic 初始输出恒为 0（零初始化生效）；
- GAE 首 token 优势 0.27739 = 0.95²⁵，末 token 1.0 —— 与解析解一致；
- 真实 PPO 更新：policy loss −0.4255、value loss 0.1167、KL 0.000277、clip fraction 0.96%，
  策略与批评家梯度范数均有限且非零（0.498 / 5.10）；
- 更新后 critic 输出从 0 变为 −0.00053，确认价值头确实在学。

### 5.4 失败处理

显存不足（OOM）时自动重试；非 OOM 的致命错误一律不重试，中断产物改名保留，
以便事后判断停在哪一步，避免同一错误反复白跑。

### 5.5 检查点与早停

每 100 次尝试：评测 666 条验证集 → 保存 LoRA 适配器 + tokenizer + `value_head.pt` → 依护栏判定是否"改进"。
连续 3 次未改进即早停。`best.json` 记录最优检查点。

> 注意：`value_head.pt` 只服务于训练，推理与生成提交文件时**不需要**它。

## 6. 训练过程

### 6.1 部署中的两次返工

本轮前两次启动都因为同一类原因被推翻，记录在此以免下次重犯：

| 版本 | 现象 | 诊断 | 处理 |
|---|---|---|---|
| 第 1 次 | 52 秒/次尝试，预估 8.7 小时 | `ps` 显示进程 CPU 99%、设备利用率只有 2–3%，瓶颈是媒体解码。前两轮留下的 846 + 643 个内容寻址缓存完全没有被复用 | 合并两处旧缓存（硬链接） |
| 第 2 次 | 合并后仍 4.3 秒/条 | 守卫脚本在启动时会把已存在的 `runs/pilot_01` 整体改名（`mv` 到 `.aborted.tryN`），连刚合并进去的缓存一起搬走 | 新增 `--media-cache` 参数，把缓存指向 `out` 目录之外的固定位置 |
| 第 3 次（最终） | 15 秒/次尝试 | 缓存生效，瓶颈回到正常的「4 次媒体预处理 + 16 次前向」 | 把 attempts 从 600 收敛到 300（600 次要 2.5 h 训练 + 6 次评测） |

最终：基线评测 11 分钟（666 条，1.0 秒/条），训练 300 次尝试、总耗时 1.51 小时（含 3 次完整评测）。

### 6.2 时间线与检查点

| 检查点 | 综合评分 | 差值 | Macro-F1 | 冲突召回 | 特异度 | 混淆矩阵 | 判定 |
|---|---|---|---|---|---|---|---|
| SFT 基线 | 0.8840 | — | 0.9403 | 57/74 | 0.9139 | TP57 FP51 FN17 TN541 | — |
| 第 100 次 | **0.8908** | **+0.0068** | **0.9478** | 58/74 | 0.9088 | TP58 FP54 FN16 TN538 | 改进，**最优** |
| 第 200 次 | 0.8877 | +0.0037 | 0.9431 | 58/74 | 0.9054 | TP58 FP56 FN16 TN536 | 未超过最优 |
| 第 300 次 | 0.8936 | +0.0095 | 0.9398 | 60/74 | 0.9020 | TP60 FP58 FN14 TN534 | **跌破特异度护栏，不合格** |

第 300 次的综合评分其实最高（0.8936），但它把特异度压到 0.9020，低于「基线 − 0.01 = 0.9039」的护栏，
因此按设计规则不参与最优竞争——护栏的目的正是防止用特异度换召回。这条规则本轮真的生效了一次。

### 6.3 训练信号

- **KL(π‖π_ref)**：从 5×10⁻⁴ 单调上升到 3.8×10⁻³，说明策略在持续远离参考模型，但始终没到 10⁻² 量级；
  中途曾出现一次 0.031 的尖峰（第 240 次附近），随后回落。
- **裁剪比例**：0.04%–0.07%，远低于常见 10% 警戒线，2e-6 + 2 epoch 的组合留有余量。
- **价值损失**：0.0100 → 0.0047，下降一半。
- **优势绝对均值**：0.0712 → 0.0612 → 0.0451，逐段递减。这不是 bug，而是批评家越来越准的自然结果：
  基线越接近真实回报，优势越小，梯度也越小，后期改进自然变慢。
- **平均奖励** 0.9477，**完美样本** 1041/1200（86.8%），**非法 JSON 0 条**。
- **配额执行**：原始冲突 780 条、合成冲突 60 条、一致样本 360 条，严格 65/5/30；
  原始冲突 143 条在第 80 次尝试前即全部覆盖（GRPO 第二轮用了 191 次）。

## 8. 与两轮 GRPO 的对比

| 项目 | GRPO 第一轮 | GRPO 第二轮 | PPO（本轮） |
|---|---|---|---|
| 尝试次数 | 300 步 | 600 次 | 300 次 |
| 最优评分 | 0.8934（第 50 步） | 0.8959（第 300 次） | 0.8908（第 100 次） |
| 生成的候选 / rollout | — | 2496 | 1200 |
| 真正参与更新的样本 | — | 193 组（7.7%） | 1200 条（100%） |
| 耗时 | 3.73 h | 2.26 h | **1.51 h** |
| 冲突召回变化 | 57 → 58 | 57 → 60 | 57 → 58 |
| Macro-F1 变化 | +0.0113 | +0.0026 | **+0.0075** |

三条可以直接下的结论：

1. **样本效率的结构性改善是真实的**：GRPO 第二轮 2496 个候选只有 7.7% 进入反传，PPO 的 1200 条全部同时充当策略样本和价值回归目标。用不到一半的生成量、三分之二的耗时，拿到了同量级的综合评分增益。
2. **冲突召回没有超过 GRPO 第二轮**：PPO +1 条，GRPO R2 +3 条。原因是 GRPO 的配额把 75% 的算力压在原始冲突上，而 PPO 只给了 65%——这是我自己做的取舍（用一致样本换特异度），代价就体现在这里。
3. **情绪分类反而更好**：F1 +0.0075，而两轮 GRPO 分别是 +0.0113（第一轮）和 +0.0026（第二轮）。PPO 的逐 token 信用分配确实更有利于整体输出质量。

**不要跨轮次比最优评分。** 同一份 SFT 适配器在三次独立评测里的综合评分分别是 0.8835 / 0.8840 / 0.8847，FP 在 49–55 之间跳动。因此 0.001–0.002 量级的跨轮差异没有解释力。

## 9. 局限与下一步

**最重要的一条发现：批评家退化成了常数基线。**

诊断数据显示，V(s_T) 对终局奖励的 MAE 从 0.159 降到 0.102，V 的均值也贴住了奖励均值（0.958 对 0.963），
但**相关系数始终在 0 附近（−0.05 ~ +0.05）**。也就是说，批评家只学会了「这批数据的平均奖励约 0.96」，
并没有区分出哪一条回答更好。

根因是奖励分布极度饱和：1200 条 rollout 中 1041 条（86.8%）直接拿满分，方差太小。
由此推出的 advantage 实质上是「奖励 − 常数」，等价于一个固定基线版的 REINFORCE，
而不是真正的状态相关基线。**PPO 相对 GRPO 的结构优势在这个任务上没有被完全兑现——问题不在实现，而在奖励的可分辨性。**

下一步若要真正发挥 PPO，应该先改奖励而不是改算法：

- 把复合奖励拆细到字段级（vision / second / fused / decision 各自成为独立的时间步奖励），
  让同一 prompt 的不同回答在回报上拉开差距；
- 或引入部分正确（partial credit），例如四字段错一个得 0.75 而不是直接掉到 0.55；
- 只有在奖励方差足够时，学习式批评家才会有信息量。

其他局限：

- **增益未达显著**：配对 bootstrap 区间下界为负，幅度 +0.0068。
- **选点偏差**：最优从 3 个检查点里在同一批标签上挑出。
- **特异度趋势仍未扭住**：0.9139 → 0.9088 → 0.9054 → 0.9020 单调下滑，即使把一致样本提到 30% 也没挡住。
  这说明「多报冲突」来自奖励结构（决策项权重 0.45）本身，不是某一轮算法的副作用。
  但要注意，这是 666 条验证集上的读数；同一检查点在 734 条测试集上的追问率是 17.4%，
  低于第二轮的 18.3%（见第 10 节），所以「模型越来越爱追问」这个结论**只在验证集内部成立**，
  不宜外推到真实分布。
- **单 prompt 只采 1 条**：为控制耗时没对同一 prompt 多次采样，同一状态的价值估计方差偏大。
- **媒体预处理是主要成本**：4 个不同 prompt 要各做一次预处理，占用单次尝试约一半时间。
  若改回「1 prompt × K 候选」的形状可以省一半时间，但那会削弱 PPO 的批次多样性优势。
