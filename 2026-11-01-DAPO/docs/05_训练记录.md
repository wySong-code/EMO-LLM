最后一项是本轮唯一的信息缺口：训练信号的解释只能靠「组级统计 + 奖励分布」这一层（见 07 文档第 5 节），不能说「loss 收敛/发散」。若还要做同类实验，应在 `cycle` 字典里补 `policy_loss`、`kl`、`grad_norm` 三个字段——三个都是现成变量，改一行即可。

### 6.3 DAPO 四项补丁的实际生效情况（`cycles.jsonl` 全 300 步统计）

| 指标 | dapo7b | dapo7b_legacy | 对照：7B GRPO |
|---|---|---|---|
| 每步尝试组数 | 5.8 | 5.7 | 8 |
| 其中 all_correct | 5.09（**88%**） | 5.03（**88%**） | 7.2（90%） |
| 有效组（active） | 0.50 | 0.49 | 0.8（10%） |
| 每步更新次数 | 0.93 | 0.90 | 0.2 |
| **零更新步数** | 160/300（53%） | 165/300（55%） | 240/300（80%） |
| `clip_upper`>0 步数 | 8/300 | 7/300 | 0 |
| `clip_lower`>0 步数 | 47/300 | 42/300 | — |
| hard_pool 末值 | 45 | 51 | — |

对应四项补丁：

1. **Clip-Higher**：`clip_upper>0` 仅 8/300 步 → 上界几乎从未被触碰，**该补丁在本任务中未生效**（梯度幅度太小，token 概率比始终落在 ε_low 内）。
2. **Dynamic Sampling（filter_groups）**：确实生效——全对组全部被过滤，不再参与梯度。零更新步从 GRPO 的 80% 降到 53%，**是四项里唯一有实质效果的**。但 88% 的组本就全对，过滤后每步只剩 0.5 个有效组，梯度极小。
3. **Token-level Loss**：已实现并全程启用，无法与其它改动单独归因。
4. **Overlong Reward Shaping**：`token_limit_hits=0`，从未触发，**本任务无过长样本**。

### 6.4 提交产物

`scripts/run_submission.sh` 按 `best.json` 的 `source` 导出台 Kaggle 格式 CSV（734 条）。但两臂的 `best.json` 是按**训练口径**（冲突召回）选的 step 200 / step 300，而官方口径的最佳点都在 step 50 —— 直接用它导出，交出的是官方分最低的几个检查点之一。

因此 11-05 补导出时改用 `scripts/run_submission_ckpt.sh`（显式指定检查点，不读 `best.json`），两臂各导 step_0050，并行执行：

```bash
bash scripts/run_submission_ckpt.sh dapo7b 50 dapo7b_step50 1
bash scripts/run_submission_ckpt.sh dapo7b_legacy 50 dapo7b_legacy_step50 3
```

| 目录 | 来源 | 验证集官方口径 | 测试集行数 | 报冲突 | 推理耗时 | 解析失败 |
|---|---|---|---|---|---|---|
| `submissions/dapo7b_step50/` | dapo7b `step_0050` | 0.937556 | 734 | 144 (19.6%) | 21.2 min | 0 |
| `submissions/dapo7b_legacy_step50/` | dapo7b_legacy `step_0050` | 0.937508 | 734 | 141 (19.2%) | 21.5 min | 0 |

两臂都是 `parse_ok=734/734`、`fallback=0`（没有一条退化成 VT prompt），说明 VA 那 347 条的音频链路在测试集上完整走通。逐样本对照：主臂与 7B SFT 提交有 23 条不同（冲突位 18、情绪位 7），legacy 有 19 条（17 / 4），差异幅度与既有提交之间 1.2–3.3% 的量级一致。

台账（含两份提交的 sha256 与历史 6 份提交的测试集对照）见 [08_提交台账.md](08_提交台账.md)，由 `_audit/build_submission_ledger.py` 现场生成。

**上榜结果（11-05 提交，改写原判断）**：

| 提交 | 验证集官方口径 | 榜分 | 与 7B SFT（0.93243） |
|---|---|---|---|
| `dapo7b_legacy_step50` | 0.937508 | **0.93580** | +0.00337 |
| `dapo7b_step50` | 0.937556 | 0.93345 | +0.00102 |

原先写的「验证集 0.9375 低于 SFT 0.940752，所以不该用 DAPO 交付」**在榜上不成立**：两臂都高于 7B SFT，legacy 甚至排到全项目第二，只比榜首 3B GRPO（0.93638）低 0.00058。但 legacy 与 7B GRPO step150（0.93577）只差 0.00003，低于 0.002 的可判阈值，**只能说「与榜首并列」，不能说「DAPO 最强」**。score_focused 的 +0.0010 同样不可判。详见 [06_结果分析 §7](06_结果分析.md)。

## 7. 复现

```bash
cd ~/grpo_mm/MM-Emotion-Combined-SFT-20261026/2026-11-01-DAPO
mkdir -p logs
setsid nohup bash scripts/run_dapo.sh > logs/launcher.log 2>&1 < /dev/null &
# 对照臂
DAPO_RUN_TAG=dapo7b_legacy DAPO_REWARD_PROFILE=legacy DAPO_DECISION_BONUS=0 \
  setsid nohup bash scripts/run_dapo.sh > logs/launcher_legacy.log 2>&1 < /dev/null &
# 完成后导出提交
bash scripts/run_submission.sh                      # 跟随 best.json（训练口径选点）
DAPO_RUN_TAG=dapo7b_legacy bash scripts/run_submission.sh   # 对照臂
# 官方口径最佳点（推荐）：显式指定检查点，两臂并行
bash scripts/run_submission_ckpt.sh dapo7b 50 dapo7b_step50 1
bash scripts/run_submission_ckpt.sh dapo7b_legacy 50 dapo7b_legacy_step50 3
```
